F02 CROSS-MODULE CALL GRAPH: tests/benchmarks/sample_jobs/small_project/
=========================================================================

Scope: every call that crosses a module boundary in cli.py, data_loader.py,
reporter.py, transformer.py, validator.py. Line numbers refer to the source
files as read on 2026-11-28. Calls into the standard library are not
counted as cross-module calls. Intra-module calls appear only where they
extend a chain that started with a cross-module call.

1. MODULE DEPENDENCY SUMMARY
----------------------------

  cli.py         imports: data_loader.load, transformer.apply,
                          validator.validate, reporter.write
  reporter.py    imports: validator.ValidationReport (annotation only)
  data_loader.py imports: nothing from the package
  transformer.py imports: nothing from the package
  validator.py   imports: nothing from the package

cli.py is the only module that makes cross-module function calls. It is the
sole orchestrator. data_loader, transformer, and validator are leaves with
respect to the package. reporter depends on validator for a type and for
attribute access on the object it receives, but never calls a validator
function.

Total cross-module function calls: 4 (all made by cli.main).
Total cross-module attribute or property accesses: 2 kinds (see section 3).


2. CROSS-MODULE FUNCTION CALLS
------------------------------

All four calls happen inside cli.main, in the try block at cli.py:53-58.
They run in this fixed order, and each output feeds the next call.

CALL 1
  Caller : cli.main                       cli.py:54
  Callee : data_loader.load               data_loader.py:38
  Args   : args.file (str), a path to a .csv or .json file
  Returns: list[dict], one dict per record. Bound to `records`.
           CSV rows: every value is a str (csv.DictReader).
           JSON rows: whatever json.load produced (any JSON type).
  Raises : ValueError (unsupported suffix, missing CSV columns, JSON root
           not an array, malformed JSON via JSONDecodeError which is a
           ValueError subclass), FileNotFoundError (from open).
           All of these are caught at cli.py:59.

CALL 2
  Caller : cli.main                       cli.py:55
  Callee : transformer.apply              transformer.py:47
  Args   : records (list[dict]) from CALL 1,
           args.steps (list[str]), default DEFAULT_STEPS
           ["strip_whitespace", "normalize_value", "add_flag"]
  Returns: list[dict], new list of transformed copies. Rebinds `records`.
  Raises : ValueError for unknown step names (transformer.py:51).
           ValueError or TypeError can also escape from add_flag
           (transformer.py:43) when it runs on a non-numeric value, for
           example if the user passes --steps add_flag without
           normalize_value. ValueError is caught; TypeError is not.

CALL 3
  Caller : cli.main                       cli.py:56
  Callee : validator.validate             validator.py:67
  Args   : records (list[dict]) from CALL 2,
           args.rules (list[str]), default DEFAULT_RULES
           ["has_id", "value_non_negative", "name_not_empty"]
  Returns: ValidationReport (dataclass: total, passed, failed, results).
           Bound to `report`.
  Raises : ValueError for unknown rule names (validator.py:72).
  Note   : an empty list (--rules with no values) is falsy, so
           `rules or list(_RULES)` at validator.py:69 runs ALL rules,
           not zero rules.

CALL 4
  Caller : cli.main                       cli.py:57
  Callee : reporter.write                 reporter.py:53
  Args   : report (ValidationReport) from CALL 3,
           fmt=args.format (str, "text" or "json"),
           dest=args.output (str or None)
  Returns: None. Side effect: prints to stdout, or writes dest file.
  Raises : OSError from Path.write_text if dest is not writable. This is
           not in the except clause at cli.py:59 and would surface as a
           traceback.

6. DATA FLOW ALONG THE MAIN PATH
--------------------------------

  args.file
    -> data_loader.load          -> list[dict]        (strings for CSV)
    -> transformer.apply         -> list[dict]        (value now float,
                                                       flagged added)
    -> validator.validate        -> ValidationReport
    -> reporter.write            -> None (stdout or file)
  report.ok -> sys.exit(0 or 1)

The data contract between stages is an untyped list[dict]. Nothing checks
that transformer output still has the keys validator reads. The only
guard is the keys' default values: validator.py:26 treats a missing "id"
as a failure, and validator.py:34 and 43 default "value" and "name".


7. CROSS-MODULE RISKS FOUND WHILE TRACING
-----------------------------------------

  1. Exception gap. cli.py:59 catches only ValueError and
     FileNotFoundError. OSError from reporter.write (reporter.py:57),
     PermissionError and IsADirectoryError from data_loader.load (open),
     and TypeError from add_flag escape as tracebacks.

  2. Empty --rules runs every rule (validator.py:69). An empty --steps is
     a no-op (transformer.py:52). The two list arguments behave
     differently for the same input shape.

  3. Step order is caller-controlled. add_flag (transformer.py:43) calls
     float() on the raw value. If the user lists add_flag before
     normalize_value, or omits normalize_value, a non-numeric CSV value
     raises ValueError and the run exits with code 2.

  4. Shared mutable state. transformer.apply copies the list but
     strip_whitespace returns a new dict, normalize_value and add_flag
     call dict(record). Records are not mutated in place, so
     data_loader.load_json output is safe. The shallow copy would not
     protect nested values.

  5. Structural coupling reporter -> validator (section 3, ACCESS B).
     A field rename in ValidationReport or RecordResult breaks reporter
     at runtime only.

  6. Load-order dependency. The step and rule registries fill when the
     module is imported. cli.py imports both, so it works today. Any new
     entry point that imports only `apply` by name still works, but one
     that never imports the module would see empty registries.
