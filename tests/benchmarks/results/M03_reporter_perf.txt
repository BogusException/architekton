M03 PERFORMANCE BOTTLENECKS: reporter.py (59 lines)

Method: static read of the source, plus a timing run on a ValidationReport
with 100,000 records (best of 3, CPython). Multipliers marked "measured" come
from that run. The others are estimates.
N+1 patterns: none. The one I/O call is a single write at the end.

Baseline: to_json (100k records) = 0.061 s (all pass) to 0.089 s (all fail).
to_text with 100k failing records = 0.028 s.

------------------------------------------------------------------
1. Whole output built in memory before one write  [HIGH on large reports]
------------------------------------------------------------------
Location: _text_lines() lines 13-28, to_text() line 32, to_json() lines
36-50, write() lines 55-59.

Text mode builds a list of line strings, joins them into one large string,
and then writes it. JSON mode builds the full nested dict (one dict per
record), then json.dumps builds the full string, then write_text or print
sends it. At 100k failing records the intermediate structures are several
times larger than the final output, and nothing appears on screen until the
last record is formatted.

Fix: stream. Write each line (or each JSON record) to the destination as it
is produced.

    def write(report, fmt="text", dest=None):
        out = open(dest, "w") if dest else sys.stdout
        try:
            for line in _text_lines(report):   # make this a generator
                out.write(line)
                out.write("\n")
        finally:
            if dest:
                out.close()

For JSON, write the header fields by hand and emit one json.dumps(record)
per record, separated by commas, inside "records": [ ... ].

Estimated improvement: 2x to 3x lower peak memory for the output stage on
large reports. Wall time is about the same (1.0x to 1.1x). Time to first
output drops from "after everything" to near zero. Not measured.

------------------------------------------------------------------
2. print() of one huge string to stdout  [MEDIUM]
------------------------------------------------------------------
Location: line 59.

A single print() of a multi-megabyte string blocks until the terminal or
pipe accepts all of it. For a pipe whose reader is slow, the pipeline stalls
at this call. The stdout buffer is the only mitigation, and it is small.

Fix: same as item 1 (smaller writes let a downstream reader start early).
Avoid sys.stdout.flush() per line, which would make it slower.

Estimated improvement: no CPU gain. Latency to first byte improves
from the full formatting time to about 0.

------------------------------------------------------------------
3. indent=2 in json.dumps  [MEDIUM]
------------------------------------------------------------------
Location: line 50.

With indent set, the stdlib json encoder skips the C fast path
(c_make_encoder is only used when indent is None) and falls back to the
pure-Python iterencode. For 100k records:

Measured: indent=2 0.089 s vs compact (separators=(",", ":")) 0.083 s
= 1.07x. The gap is small here because the test dicts are small, and the
output size is also about 1.8x larger with indent. Larger or deeper
records widen the gap.

Fix: make indent optional (indent=None for machine consumers, which
is the common use of --format json), or print one compact record per line
(JSON Lines).

Estimated improvement: 1.07x measured on time, about 1.8x smaller output
(and so less write time and disk or pipe traffic).

------------------------------------------------------------------
4. Intermediate record dicts in to_json  [LOW]
------------------------------------------------------------------
Location: lines 41-48.

Every RecordResult is copied into a new dict just so json.dumps can
serialize it. dataclasses.asdict is slower than this hand-built dict, so
the current code is already the faster of the usual options. Streaming
(item 1) removes the copy as a side effect, because each dict can be
discarded right after it is written.

Estimated improvement: included in item 1.

------------------------------------------------------------------
5. Repeated .append() and f-string per failure line  [LOW]
------------------------------------------------------------------
Location: lines 25-27.

Text mode makes one f-string per failing record, plus one per failure
message. Using lines.extend() with a generator saves method-lookup
overhead, but the gain is within noise.

Measured: 0.028 s for 100k failing records. Not worth changing alone.

Estimated improvement: 1.05x. Skip.

------------------------------------------------------------------
6. Passing records are iterated in text mode  [LOW]
------------------------------------------------------------------
Location: lines 23-24.

The loop visits all records to find the failures. If validate() kept a
separate list of failing results, the reporter would iterate only the
failures. On a file with 1% bad rows, the loop does 100 times the needed
iterations.

Fix: add failed_results to ValidationReport (or filter once in validator).

Estimated improvement: up to 20x on this loop when failures are rare
(estimated, loop only). In total reporter time, a clean report is
already fast, since text mode on a passing report skips the loop
entirely (line 20), so the real gain shows only on mostly-passing files
with some failures.

------------------------------------------------------------------
Ranked summary
------------------------------------------------------------------
Rank  Finding                              Est. gain                Effort
1     Stream output instead of building    2x to 3x less memory     medium
2     Avoid one giant print()              latency only             small
3     Drop indent=2 for json               1.07x measured           trivial
4     Skip intermediate dicts              part of item 1           n/a
5     f-string / append tuning             1.05x                    skip
6     Keep a failures-only list            up to 20x on the loop    small

For the sizes this pipeline handles (under 100k records), the reporter takes
under 0.1 s and is not the bottleneck. Fix items 1 and 3 only if reports
reach millions of records.
