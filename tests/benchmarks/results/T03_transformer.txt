Purpose

transformer.py applies an ordered chain of named transformations to a list of record dicts. A transformation takes one record and returns a modified copy. Transformations register themselves by name in the module-level dict _REGISTRY (line 11) through the @register decorator. apply() resolves the names and runs every record through each step in order.

Key functions

- register(name) (lines 14-19): decorator factory. It stores the function in _REGISTRY under the name and returns the function unchanged, so it can still be called directly.
- normalize_value(record) (lines 23-30): copies the record and casts "value" to float. A missing key is treated as 0. A TypeError or ValueError from float() sets the value to 0.0.
- strip_whitespace(record) (lines 34-36): returns a new dict where every string value is stripped. Other types are kept as they are.
- add_flag(record) (lines 40-44): copies the record and sets "flagged" to True when float(value) > 100.
- apply(records, steps) (lines 47-55): checks that every step name is registered (raises ValueError listing the unknown names), copies the input list, then for each step rebuilds the list by calling the step function on each record.

Design choices

- A registry plus decorator makes steps easy to add and lets the CLI pass plain strings.
- Steps do not modify their input. Each makes a new dict, and apply() makes a new list, so the caller's data stays intact.
- All step names are checked before any record is processed. A typo fails at once and does not leave half-transformed data.
- Steps run in the order given by the caller, so order is the caller's responsibility.
- Each step is one small pure function, which is easy to unit test.
- The threshold 100 in add_flag is hard-coded.

Risks and missing error handling

1. add_flag is not safe (line 43). It calls float() with no try/except, unlike normalize_value. If it runs before normalize_value, or without it, a non-numeric value raises ValueError, and a None value raises TypeError. cli.py catches ValueError and reports a generic message with no record or step name. TypeError is not caught and gives a traceback. The step order dependency is neither enforced nor documented.
2. normalize_value hides bad data (lines 26-29). Any non-numeric value silently becomes 0.0. That value then passes the value_non_negative rule, so the validator can never report "not numeric" for it. Corrupt input is turned into valid-looking data. An empty string also becomes 0.0.
3. float() accepts "nan", "inf" and "-inf". NaN is not replaced by 0.0 in normalize_value. NaN > 100 is False, so NaN records are never flagged, and NaN is not below 0, so it also passes validation.
4. A missing "value" key is replaced by 0 (out.get("value", 0)), and normalize_value then adds a "value" field to a record that did not have one. This hides a missing column in JSON input.
5. Copies are shallow (dict(record)). Nested lists or dicts in a JSON record are shared between input and output, so the "does not modify input" claim holds only for flat records.
6. strip_whitespace does not touch nested strings, and it does not strip keys. A key with trailing space stays as is.
7. register() silently overwrites an existing name. Two modules that register the same name will replace each other with no warning.
8. _REGISTRY is global and mutable, so tests can leak state between runs.
9. Non-dict items in the input list (from a malformed JSON file) cause TypeError or AttributeError, with no useful message.
10. apply() builds a full new list for every step. For N records and S steps this is S passes over memory. That is fine for the sample size but not for large inputs.
