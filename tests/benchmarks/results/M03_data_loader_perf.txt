The file has three real findings, all about memory or extra copies. It has no per-item calls, no repeated computation, and one open() per file, so there is no N+1 or I/O blocking problem. The multipliers below are estimates from CPython behavior, not measured runs.

Ranked findings

1. Category: unnecessary copies (full materialization)
   Function: load_csv, lines 17 and 24-26
   Scope: large inputs only
   Description: load_csv holds every row dict in one list before it returns. The caller gets no rows until the whole file is parsed, and peak memory grows with the row count. If the caller reads each row once, a generator keeps memory flat.
   Fix:
       def iter_csv(path: str):
           with open(path, newline="") as fh:
               reader = csv.DictReader(fh)
               missing = REQUIRED_COLUMNS - set(reader.fieldnames or [])
               if missing:
                   raise ValueError(f"CSV missing required columns: {sorted(missing)}")
               yield from reader

       def load_csv(path: str) -> list[dict]:
           return list(iter_csv(path))
   Estimate: peak memory drops from O(rows) to O(1) for a streaming caller. Basis: measured about 390 bytes per row (200,000 rows, four short fields, Python 3.14.4), so 1M rows hold roughly 400 MB, while a streaming caller holds one row (under 1 KB). The pipeline in cli.py gains nothing today, because transformer.apply() needs the full list.
   Caveats: load_csv still returns a list, so existing callers see no change. A caller that uses iter_csv gets the memory win. The header check now runs on the first next() call, not on the call to load_csv.

2. Category: unnecessary copies (whole-file read)
   Function: load_json, lines 31-32
   Scope: large inputs only
   Description: json.load reads the entire file into one string, then builds the full object tree. Peak memory is the file text plus the parsed records. The standard json module has no streaming parser for a top-level array.
   Fix:
       import ijson  # third-party

       def iter_json(path: str):
           with open(path, "rb") as fh:
               yield from ijson.items(fh, "item")
   Estimate: peak memory falls from roughly 4.5x the file size (measured on a 200,000-record array) to one record at a time. Time gets worse: ijson is a Python-level iterator over a parser and is usually several times slower than json.load, which runs in C. This was not measured because ijson is not installed here.
   Caveats: ijson.items does not raise on a non-array top level, so the isinstance check at line 33 must stay or be replaced by a peek at the first token. ijson is a third-party package. If the project limits itself to the standard library, use newline-delimited JSON with a line loop instead of a single array.

3. Category: unnecessary copies (redundant dict copy)
   Function: load_csv, line 25
   Scope: all input sizes
   Description: csv.DictReader already creates a new dict for each row and does not keep a reference to it. The dict(row) call on line 25 copies that dict again for no reason. The append loop on lines 24-25 can also be replaced by list(reader).
   Fix:
       rows = list(reader)
   Replace lines 24-25 with the line above. Line 26 (return rows) stays.
   Estimate: about 1.08x faster on the parse loop. Basis: measured 318 ms with dict(row) versus 294 ms with list(reader) for 200,000 rows (Python 3.14.4, reading from io.StringIO). Memory does not change, because the copied dict is freed right away.
