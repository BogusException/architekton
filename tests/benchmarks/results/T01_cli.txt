Source reviewed: cli.py (66 lines, read in full). Sibling modules read only for the calls cli.py makes: data_loader.py, transformer.py (apply, normalize_value, strip_whitespace), validator.py (validate, ValidationReport), reporter.py (write). No source file was changed.

Purpose

cli.py is the command-line entry point for the small_project pipeline. It takes one .csv or .json file, applies named transformation steps, checks the records against named validation rules, and writes a text or JSON report to stdout or to a file. The module holds no processing logic. It only parses arguments and connects four stages in a fixed order: load, transform, validate, report.

Key functions

main() -> None (cli.py:20-61)
Builds the argparse parser, parses sys.argv, runs the pipeline, and ends the process with sys.exit. It never returns normally. It does these steps in order:
1. Parses the positional file argument and the options --steps, --rules, --format, and --output (cli.py:21-51).
2. Calls load(args.file) (cli.py:54). Signature: load(path: str) -> list[dict], data_loader.py:38. Dispatches on file extension to load_csv or load_json. Raises ValueError for an unsupported extension, a CSV without the required columns, or a JSON root that is not an array. Raises FileNotFoundError for a missing file.
3. Calls apply(records, args.steps) (cli.py:55). Signature: apply(records: list[dict], steps: list[str]) -> list[dict], transformer.py:47. Runs each named step over every record, in order. Raises ValueError for an unknown step name.
4. Calls validate(records, args.rules) (cli.py:56). Signature: validate(records: list[dict], rules: list[str] | None = None) -> ValidationReport, validator.py:67. Runs each named rule over every record. An empty or missing rules list means all rules. Raises ValueError for an unknown rule name.
5. Calls write(report, fmt=args.format, dest=args.output) (cli.py:57). Signature: write(report, fmt: str = "text", dest: str | None = None), reporter.py:53. Writes JSON when fmt is "json", text otherwise, to dest or stdout.
6. Exits with status 0 if report.ok is True, otherwise 1 (cli.py:58). report.ok is a property that returns failed == 0 (validator.py:63-64).
7. Catches ValueError and FileNotFoundError, prints "error: <message>" to stderr, and exits with status 2 (cli.py:59-61).

Module constants
DEFAULT_STEPS (cli.py:16): strip_whitespace, normalize_value, add_flag.
DEFAULT_RULES (cli.py:17): has_id, value_non_negative, name_not_empty.
Both are used as argparse defaults for --steps and --rules.

Design choices

1. Thin orchestrator. All logic sits in the four sibling modules, so each stage can be tested without argparse or a process exit.

2. Fixed stage order: load, transform, validate, report. Validation sees transformed records, not the raw file. This ordering causes risk 5 below.

3. Stages are chosen by string name. Each sibling module owns its registry and rejects unknown names. cli.py does not check the names itself, so a bad name fails only after the file has been loaded and transformed (risk 7).

4. Exit status contract: 0 means the report passed, 1 means at least one record failed a rule, 2 means an input or usage error that the code catches. argparse also uses 2 for usage errors. The contract is weakened because Python also exits with 1 on any uncaught exception (risk 3).

5. The report is written before the exit status is set. A failed validation still produces the full report, and the exit code only signals the result.

6. Defaults are full lists, so a bare run does all the work. nargs="*" lets a user pass an empty list, but the two stages treat an empty list differently (risk 6).

7. No logging, no verbosity flag, no config file. Errors go to stderr as one line.

8. Standard library only (argparse, sys), which matches the project's stdlib-only rule for the hot path.

Risks and missing error handling

Listed roughly from most to least likely to cause a wrong result in real use.

1. cli.py:59 catches only ValueError and FileNotFoundError. Other exceptions from load, apply, or validate end the program with a traceback and exit status 1. Example: a JSON file containing [1, 2] passes load_json, since it only checks for a list (data_loader.py:33). Then apply runs strip_whitespace, which calls .items() on an int (transformer.py:36). That raises AttributeError, which cli.py does not catch. The program exits 1, the same status as a failed validation.

2. cli.py:57 write() with --output. Path.write_text can raise PermissionError or IsADirectoryError. Both are OSError subclasses, so cli.py:59 does not catch them. Example: --output /tmp/reports/ where the path is an existing directory gives an IsADirectoryError traceback and exit 1. A missing parent directory gives FileNotFoundError, which is caught and exits 2.

3. cli.py:58 and cli.py:61 share exit status 1 with uncaught exceptions. A CI job that treats exit 1 as "validation failed" will also treat a crash as a validation failure, and the reverse is also true. Fix: catch Exception at the top level and use a separate status code, for example 3.

4. cli.py:54 loads the full file into a list of dicts (data_loader.py:24-25) with no size limit. Example: a 5 GB CSV raises MemoryError, which cli.py does not catch. The program exits 1 with a traceback.

5. cli.py:55-56 with transformer.py:27-29. normalize_value replaces any non-numeric value field with 0.0 before validation runs. Example: a CSV row with value "n/a" becomes 0.0. Zero is not negative, so value_non_negative passes. The run exits 0 and reports PASSED, and the bad input is never flagged. The cli.py ordering makes the correction happen before the check.

6. Empty lists behave differently. validator.py:69 uses "rules or list(_RULES)", and an empty list is falsy. So "--rules" with no values runs all three rules, not none. Example: a user runs cli.py data.csv --rules to skip checks. All rules run, and the exit status is 1 for failures the user meant to skip. By contrast, "--steps" with no values gives an empty list, and apply runs no steps.

7. cli.py:55-56 run after load. An unknown step or rule name is found only after the whole file is loaded and transformed. Example: a 2 GB CSV with a typo in --rules spends the full load and transform time before exit 2. Checking names against the registries during argument parsing would avoid this. Likelihood is low. The cost is only wasted time.

8. Empty input passes. validator.py:64 returns True when failed == 0, and a report with zero records has failed == 0. Example: a CSV with only a header row, or a JSON file containing [], produces zero records. cli.py exits 0 and prints PASSED. An upstream export that failed and wrote an empty file looks like a successful run. Fix: reject zero records in cli.py or in validate.

9. cli.py:24 with cli.py:26-38. The positional file argument and the nargs="*" options interact. Example: python cli.py --steps strip_whitespace data.csv treats data.csv as a step name. argparse then reports "the following arguments are required: file" and exits 2, even though the file is on the command line. Placing the file before the options, or using "--" before the file, avoids this.

10. reporter.py:57 writes with no encoding argument, and the file is opened (and truncated) before the text is encoded. Example: on a system with a non-UTF-8 locale, a name with non-ASCII characters raises UnicodeEncodeError. That is a ValueError, so cli.py:59 catches it and exits 2. The output file is left partly written, and the report is lost.

11. reporter.py:59 prints to stdout with no handling for a closed pipe. Example: python cli.py big.csv | head -1 can raise BrokenPipeError when the report is larger than the pipe buffer. The traceback goes to stderr and the exit status is 1, which is misleading.

12. Missing: no check that --output is not the input file, no check on --format beyond argparse choices (which is sufficient), and no way to set an exit status for warnings. These are design gaps, not current failures.
