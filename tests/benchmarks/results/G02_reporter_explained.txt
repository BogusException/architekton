reporter.py is the last stage of the small_project pipeline. It takes a ValidationReport from validator.py and turns it into a string. The string is either plain text or JSON. The public function write() (line 53) picks the format, then sends the string to a file or to stdout. The two formatters, to_text() (line 31) and to_json() (line 35), are also public. Text mode prints a PASSED or FAILED header and three counts. If any record failed, it adds a list of failures grouped by record id. JSON mode returns the same facts as a dict, dumped with an indent of 2.

The only caller in the project is main() in cli.py, which calls write() at line 57 after load(), apply() and validate(). The user of the module is therefore either a person who runs the CLI and reads the text, or a script that reads the JSON from stdout or from the output file. A developer would import reporter directly in two cases. The first is to reuse to_text() or to_json() in new code, for example a test. The second is to add a new output format next to the existing two.

Use this module when you hold a ValidationReport and need a report for a person or a downstream tool. Do not use the logging module for this. Logging is for diagnostic events with levels and handlers, and this output is the product of the program. Do not call json.dumps on the dataclass directly. A ValidationReport is not JSON serializable as is, and to_json() renames fields into a stable shape that other tools can depend on. A templating library such as Jinja would be too much for a four-line summary. If the report grows to include tables, HTML or many sections, that is the point to change.

Several details can surprise you. First, the JSON key names differ from the dataclass names. The dataclass has passed and failed (counts), but to_json() writes pass_count and fail_count, and its "passed" key (line 38) is a boolean that comes from report.ok. Each record uses "id" where the dataclass uses record_id (line 43). Second, write() treats any fmt other than "json" as text (line 55). A typo such as "jsno" gives text output with no error. Only the CLI limits the choices. Third, _text_lines() lists failures only when the report is not ok (line 20), and a report with zero records counts as PASSED because ok only checks failed == 0. Fourth, the two output paths differ by one character. print() at line 59 adds a trailing newline, but Path.write_text() at line 57 does not, so a file written by write() has no final newline. Line 57 also uses the default text encoding of the platform, does not create missing parent directories, and silently overwrites an existing file. In cli.py, a missing directory raises FileNotFoundError and exits with code 2, but a PermissionError is not caught and shows a traceback. Finally, line 10 uses the bare import "from validator import ValidationReport". It works only when the small_project directory is on sys.path, so run the code from that directory or set PYTHONPATH.
