data_loader.py reads a data file from disk and returns it as a list of plain Python dicts. It supports two formats, CSV and JSON. The public entry point is load() at line 38. It looks at the file extension and calls load_csv() (line 15) or load_json() (line 29). The module also holds REQUIRED_COLUMNS at line 12, which is the set id, name, value and timestamp. Every other module in the pipeline expects records that have those keys.

The main caller is cli.py. It imports load() at line 10 and calls it at line 54, then passes the records to transformer.apply() and validator.validate(). You will also call it yourself in tests, or in any script that needs to feed records into the same pipeline. Application code should call load(). Call load_csv() or load_json() directly only when you already know the format and do not want the extension check.

Use this module when you want the pipeline's record shape and its error messages. The csv and json modules from the standard library do the actual parsing here, so you gain little over them for a one-off script. What you gain is a single call that picks the parser, checks the CSV header, and raises ValueError with a readable message. Use pandas instead when the data is large, when you need typed columns or dates, or when you need to filter and group. This module reads the whole file into memory and gives you no type conversion at all. Every CSV value comes back as a string, including value and timestamp, so the transformer or validator must convert them.

Encoding is the first gotcha. Both open() calls (line 18 and line 31) omit the encoding argument, so Python uses the locale default. A UTF-8 file with a byte order mark will leave the BOM attached to the first header, and "id" will not match "id" with an invisible BOM character in front. That makes load_csv() report id as missing even though it looks present. Pass encoding="utf-8-sig" if you hit this. The extension check in load() (lines 41 and 43) is case sensitive, so DATA.CSV raises "Unsupported file type" at line 45. A file with no suffix fails the same way.

The second gotcha is that validation is shallow and uneven. load_csv() checks only the header row (lines 20 to 23). A short row gets None for the missing fields, and a long row stores its extra cells under a None key, with no error either way. A completely empty CSV has no fieldnames, so you get the "missing required columns" error listing all four names. load_json() checks only that the top level is a list (line 33). It never checks that each item is a dict, and it never checks for REQUIRED_COLUMNS, so a JSON file can pass load() and then fail later in the pipeline. For errors, a missing path raises FileNotFoundError from open(), which nothing in this file catches. A malformed JSON file raises json.JSONDecodeError and a bad byte sequence raises UnicodeDecodeError. Both are subclasses of ValueError, which is why the except clause in cli.py at line 59 catches them and exits with code 2.
