validator.py checks a list of record dicts against named rules and returns a report. A rule is a plain function that takes one record and returns None if the record passes, or a string that describes the failure (see the RuleFunc alias at line 11). The decorator rule() at line 16 adds a function to the module-level registry _RULES at line 13. Three rules ship with the module: has_id (line 25), value_non_negative (line 32) and name_not_empty (line 42). The main entry point is validate() at line 67. It runs each chosen rule on each record. It returns a ValidationReport (line 56) that holds the total, passed and failed counts, plus one RecordResult (line 49) per record. The ok property at line 63 is True only when no record failed.

In this project, cli.py is the main caller. It loads and transforms the records, then calls validate(records, args.rules) and passes the report to reporter.py. reporter.py reads total, passed, failed, ok and each result's failures list. The CLI turns report.ok into exit code 0 or 1. A developer who adds a new check would use rule() to register it. A developer who builds a new front end, such as a service or a test harness, would call validate() directly. The default rule names are listed in DEFAULT_RULES in cli.py, so a new rule is not on by default until you add it there.

Use this module when the checks are small, the records are flat dicts, and you want a pass or fail report for every record with all failure reasons together. It has no dependencies and is easy to read. Use jsonschema when the rules are about shape, such as required keys, types and ranges, and you want a standard format that other tools can share. Use pydantic when you want typed models and automatic type conversion, and you want invalid data to stop the program. A bare if-check is better when you have one check in one place. This module does not do schema checks, nested data, or type conversion. It also does not stop on the first bad record, which pydantic would do by default.

Errors are collected, not raised, with one exception. validate() raises ValueError at line 72 if any requested rule name is not in _RULES. That check runs before any record is read, so a typo fails fast. cli.py catches ValueError and exits with code 2. Each failure string is prefixed with the rule name at line 80, for example "has_id: missing or empty 'id'". Every rule runs on every record, so one record can have several failures. One more detail is at line 69: "rules or list(_RULES)" treats an empty list the same as None. In cli.py, the rules option with no names gives an empty list, so all registered rules run, not none. Duplicate names in the list make that rule run twice, and each failure is reported twice.

The type checks have edge cases. value_non_negative uses float() at line 34, so the strings "5" and " 5 " pass and the bool True counts as 1. The string "nan" passes because NaN < 0 is False. A record with no "value" key passes because the default is 0, but a record with "value": None fails with "not numeric" at line 37. Only value_non_negative catches TypeError and ValueError. If a record is not a dict, has_id fails with an AttributeError at line 26, and validate() does not catch it at line 78. One bad record then crashes the whole run. has_id uses a truthiness test, so an id of 0 is reported as missing. name_not_empty calls str() at line 43, so a name of None becomes the string "None" and passes. In validate(), the record_id at line 82 is str(record.get("id", "(no id)")), so a missing id shows as "(no id)" but an empty id shows as an empty string. A rule that returns an empty string counts as a pass, because line 79 tests truthiness. The rule() decorator silently replaces an existing rule with the same name (line 19). Rules register when the module is imported, so a custom rule must be imported before validate() is called. The annotation "str | None" at line 11 needs Python 3.10 or newer. An empty records list gives total 0 and ok True, which may hide an empty input file.
