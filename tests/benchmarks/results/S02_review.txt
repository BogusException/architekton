S02 code review: small_project

Files reviewed: cli.py, data_loader.py, reporter.py, transformer.py, validator.py
Path: tests/benchmarks/sample_jobs/small_project/


cli.py

(1) What it does
Command-line entry point. main() parses a data file path plus --steps, --rules, --format and --output. It then runs load, apply, validate and write in that order. Exit codes: 0 report passed, 1 report failed, 2 ValueError or FileNotFoundError.

(2) Bugs and unhandled edge cases
1. Lines 59-61 catch only ValueError and FileNotFoundError. PermissionError, IsADirectoryError and other OSError subclasses from load() or write() escape as a traceback. So do TypeError and AttributeError from the transform and rule code (for example a JSON array of non-dicts like [1, 2, 3]).
2. Uncaught exceptions exit with code 1, the same code as "validation failed". A calling script cannot tell a failed report from a crash.
3. Line 57 calls write() before the exit code is chosen. A failing run still leaves the --output file on disk. The help text does not say this.
4. --rules with no names gives [], and validate() treats [] as "run all rules" (see validator.py). --steps with no names skips all transforms. The two options behave in opposite ways for the same input.
5. The imports (from data_loader import load) work only when the script runs from its own directory or that directory is on sys.path. Running it as a package module fails.
6. Step order is not checked. add_flag before normalize_value can crash on raw CSV strings such as "n/a".

(3) Improvement
Add "except OSError" to the handler, and exit 3 for unexpected errors so that exit 1 means only "report failed". Add a one-line message that names the step or rule that raised.


data_loader.py

(1) What it does
Reads a .csv or .json file and returns a list of dicts. load() picks the loader from the file extension. load_csv() checks that id, name, value and timestamp exist in the header. load_json() checks only that the top level is a list.

(2) Bugs and unhandled edge cases
1. load_csv() returns every field as a string. load_json() returns native types. Downstream code behaves differently for the same data: has_id accepts the CSV id "0" but rejects the JSON id 0.
2. load_json() does not check required keys or that each item is a dict. A record with no "value" key loads and then defaults to 0 in later stages, so it passes the whole pipeline.
3. open() has no encoding argument. The result depends on the system locale. A UTF-8 file with a BOM produces a first header of "﻿id", and the "missing required columns" error then names "id" even though the column looks present.
4. Line 41 compares p.suffix to ".csv" exactly. "DATA.CSV" is rejected as unsupported.
5. Short CSV rows give None for the missing fields. Extra cells are stored under the key None, as a list. Neither case is checked.
6. A headers-only CSV or an empty JSON array returns []. Nothing warns that no data was loaded.
7. The "timestamp" column is required here but never read by any other module.

(3) Improvement
Open files with encoding="utf-8-sig". Run one shared check, after both loaders, that every record is a dict and has the required keys. This removes the CSV/JSON difference in item 2.


reporter.py

(1) What it does
Turns a ValidationReport into text (to_text) or JSON (to_json). write() sends the result to a file or to stdout.

(2) Bugs and unhandled edge cases
1. write() calls Path(dest).write_text(content) with no trailing newline, but the stdout branch uses print(), which adds one. The two outputs differ by a final newline.
2. write_text() has no encoding argument. Non-ASCII record ids or failure messages can fail or garble on a non-UTF-8 locale.
3. fmt is not validated. Any value other than "json" (for example "xml" or "JSON") silently gives text output.
4. dest="" is falsy, so an empty --output string writes to stdout instead of failing.
5. A missing parent directory raises FileNotFoundError. cli.py reports it as exit 2 with the raw OS message, which looks like an input-file error.
6. A record with an empty id prints as "Record :" and one with id None prints as "Record None:". The report has no row number, so duplicate or empty ids cannot be told apart.
7. The text report lists failures only when the report failed, and it lists every failed record with no limit. A large failing file produces a very long report.

(3) Improvement
Raise ValueError for an unknown fmt, and use a dict of format name to function instead of the inline conditional. Add the row index to RecordResult and print it in both formats.


transformer.py

(1) What it does
Holds a registry of named record transformations (normalize_value, strip_whitespace, add_flag), added with the @register decorator. apply() checks that all step names exist, then runs each step over every record in the order given. Each step returns a copy.

(2) Bugs and unhandled edge cases
1. add_flag (line 43) calls float() on "value" with no guard. With --steps add_flag alone, a CSV value such as "n/a" raises ValueError, and a None value raises TypeError. The error names no step or record.
2. normalize_value replaces any unparseable value with 0.0, so "n/a", None, "" and "1,234" all become 0.0. value_non_negative then passes them. The "'value' is not numeric" branch cannot fire after the default steps.
3. float() accepts "nan", "inf" and "-inf". normalize_value passes them through, and NaN also passes value_non_negative because NaN < 0 is False.
4. A missing "value" key becomes 0 (out.get("value", 0)) instead of being reported.
5. strip_whitespace handles only top-level strings. Nested dicts and lists in JSON records are not cleaned.
6. register() overwrites an existing name without warning.
7. float(True) is 1.0, so a JSON boolean in "value" is accepted as a number.

(3) Improvement
Make normalize_value set value to None (or raise a ValueError that names the record) when parsing fails, instead of 0.0. Let add_flag reuse the same parsing so the two cannot disagree.


validator.py

(1) What it does
Holds a registry of named rules (has_id, value_non_negative, name_not_empty). Each rule returns None on pass or a message on failure. validate() runs the chosen rules on every record and returns a ValidationReport with per-record results and totals. report.ok is true when failed == 0.

(2) Bugs and unhandled edge cases
1. Line 69: "rules or list(_RULES)" treats an empty list as "all rules". A caller who passes [] gets every rule.
2. name_not_empty uses str(record.get("name", "")). When "name" is present and None (JSON null), str(None) is "None", which is non-empty, so the record passes.
3. has_id uses "not record.get('id')". The JSON id 0 and the empty string both fail, but the CSV string "0" passes.
4. value_non_negative: NaN passes (NaN < 0 is False). A huge int such as 10**400 raises OverflowError in float(), which is not caught.
5. A rule that raises an exception stops the whole run. One bad record loses all results.
6. A non-dict record (from a JSON array like [1, 2]) raises AttributeError on .get.
7. total=0 gives ok=True. An empty input is reported as "PASSED".
8. record_id is built from the id with a "(no id)" default only when the key is missing. A key that exists with an empty or None value gives "" or "None".
9. timestamp is never validated, so a blank or invalid timestamp passes.

(3) Improvement
Use "rules if rules is not None else list(_RULES)" so an empty list means no rules. Wrap each rule call in try/except and record "rule_name: raised X" as a failure for that record, so one bad record does not abort the run.


Cross-file issues

1. Default steps hide the bad values the default rules look for. cli.py runs normalize_value before validation, which turns None, "n/a" and "1,234" into 0.0. The "not numeric" check in value_non_negative is then dead code in the default run.
2. Exit code 1 has two meanings (failed report, uncaught crash). See cli.py item 2.
3. Empty input passes at every layer: the loader returns [], the validator returns ok=True, the reporter prints "PASSED", and cli.py exits 0.
4. CSV and JSON records have different shapes and different checks, so the same logical record can pass or fail depending on the file type.
