Purpose

validator.py checks a list of processed records (dicts) against named rules. Each rule is a function that takes one record and returns None when the record passes, or a string that describes the failure. The module ships three built-in rules: has_id, value_non_negative, and name_not_empty.

The public entry point is validate(). It runs the selected rules, or all registered rules when none are named, against every record. It returns a ValidationReport with total, passed and failed counts, a list of per-record RecordResult objects, and an ok flag that is True when failed is 0.

The module does no I/O and does not change the input records.

Design choices

Rules are plain functions. A decorator registers each one under a name in a module-level dict. Importing the module registers the built-in rules. A new rule needs one decorated function. There is no rule class and no config file.

A rule returns a message or None. The validator does not need to know how a rule fails, so each rule stays short. The cost is that the message is free text. A caller that wants the rule name alone must split the "rule_name: message" string (line 80). No error code exists.

Errors are collected per record, not raised. Every selected rule runs on every record, even after an earlier rule fails. A record with three bad fields gets three messages in one pass. The design aims to report bad data, not stop on it.

Only one path raises: an unknown rule name (line 72). That is a caller mistake, so raising is a reasonable choice. Bad record content does not raise by design. The rules return a message instead.

The summary counts are computed once at the end (lines 87-91). failed is len(results) minus passed, so the two always add up to total.

Trade-offs I can see:
The registry is global and mutable. Any code that calls rule() changes the default behavior of validate() for the rest of the process.
Rule order in the default run follows dict insertion order, which is the order the decorated functions are imported.
There is no early exit per record. This gives complete reports but costs more rule calls on bad data.
The rule contract is checked only by convention. The module does not check the return type.


Risks and missing error handling

1. validate, line 69: "rules or list(_RULES)" treats an empty list the same as None. A call such as validate(records, rules=[]) runs every rule, not zero rules. A caller that builds its rule list from a filter that matches nothing gets a full run and no warning.

2. validate, line 78: the rule call is not wrapped in try/except. If a rule raises, the exception leaves validate() and no report is returned. A record that is not a dict (for example None or a string) reaches has_id at line 26 and raises AttributeError from record.get. This conflicts with the design goal of reporting bad data. The same input would also fail at line 82.

3. validate, line 82: the record_id fallback gives different labels for similar cases. A record with no "id" key gets "(no id)". A record with "id": None gets "None" (str(None)). A record with "id": "" gets an empty string. The labels do not match, and a report reader cannot tell a missing id from a null id.

4. has_id, line 26: the check is a truthiness test. An id of 0 is reported as "missing or empty 'id'", which may be wrong when 0 is a valid numeric id. There is no type check, so any non-empty value passes, including a list or a dict.

5. value_non_negative, line 34: a record without a "value" key is read as 0 and passes. The rule does not flag a missing value. Whether that is correct depends on the record schema, which the module does not define.

6. value_non_negative, line 34: float() accepts the strings "nan", "inf" and "-inf", and bool values (True becomes 1.0). float("nan") < 0 is False, so a NaN value passes silently. There is no finiteness check.

7. value_non_negative, lines 36-37: only TypeError and ValueError are caught. Any other exception from float() propagates out of validate(), as in risk 2.

8. name_not_empty, line 43: str(record.get("name", "")) converts None to "None". A record with "name": None therefore passes, because "None" is not empty. A name of 0 becomes "0" and also passes. The check does not match its message.

9. Missing keys are handled in different ways. has_id (line 26) and name_not_empty (line 43) fail a missing key. value_non_negative (line 34) passes a missing key. A record with no value field and a record with no name field get different results.

10. Empty input, lines 87-93: validate([]) returns total 0, passed 0, failed 0 and ok True. An empty batch passes. A caller that expects at least one record must check total.

11. Python version, lines 11, 13, 25, 42, 67: the annotations "str | None", "list[str] | None" and "dict[str, ...]" are evaluated when the module loads, because there is no "from __future__ import annotations". The "X | None" form needs Python 3.10 or later. On Python 3.9 the import fails with TypeError.

12. Duplicate rule names, line 19: decorator overwrites an existing entry with no error. If two modules register the same name, one rule disappears without a warning.

13. Rule return contract, line 79: the check is "if msg:". A rule that returns "" is counted as a pass. A rule that returns a truthy non-string (for example True) is stored as the failure text "rule_name: True". Nothing checks the str | None contract.

14. Not covered by any rule: duplicate record ids. Two records with the same id both pass. This is a scope gap, not a bug in the code. The module does not claim to check uniqueness.
