cli.py is the command-line entry point for the small_project data pipeline. It does not hold any processing logic of its own. The main() function (line 20) parses arguments, then runs four steps in a fixed order: load from data_loader (line 54), apply from transformer (line 55), validate from validator (line 56), and write from reporter (line 57). It takes one required file path, plus options for the transformation steps, the validation rules, the output format (text or json) and an optional output file. Two constants at lines 16 and 17, DEFAULT_STEPS and DEFAULT_RULES, set what runs when you pass nothing.

The users are people who want to check a CSV or JSON file from a shell, and scripts or CI jobs that need a pass or fail answer. The exit code carries that answer. The code exits 0 when every record passes (line 58), 1 when the report has failures, and 2 when the run itself breaks (line 61). A new developer will also meet this file first, because it shows in one screen how the four other modules connect.

Use cli.py when you have a file on disk and want the whole pipeline with no Python code. It is the right tool for quick checks, shell pipelines and cron jobs. Call the underlying modules directly when you work with records already in memory, when you need your own transformation or rule, or when you want the ValidationReport object and not rendered text. The cli.py file only offers the registered steps and rules by name, so it cannot take a custom function. For heavy or large-scale data work, a dedicated tool such as pandas is a better fit than this small pipeline.

Several gotchas affect day-to-day use. The imports at lines 10 to 13 are flat (from data_loader import load), so you must run the file from its own directory or put that directory on the Python path. The main() function takes no arguments and calls parser.parse_args() at line 51 with no argv, so tests must patch sys.argv. The steps and rules options use nargs="*" (lines 27 and 34), so they swallow every word after them, including the file path. Put the file path first. Also, an empty list behaves differently for each option. Passing the steps option with no values runs zero transformations, but passing the rules option with no values runs every registered rule, because validate() treats an empty list as "all rules" (validator.py line 69). That is more than the three defaults in DEFAULT_RULES.

Error handling is narrow. The except clause at line 59 catches only ValueError and FileNotFoundError. Bad file extensions, unknown step or rule names and malformed JSON all land there and give exit code 2 with a short message. Other errors, such as PermissionError or a failed write to the output file (reporter.py write(), which calls write_text with no guard), show a full traceback and exit with code 1. That is the same code that means "validation failed", so a script cannot tell the two cases apart. File extension matching in load() is case sensitive, so data.CSV is rejected. Finally, the sys.exit calls at lines 58 and 61 sit inside the try block. This works today because SystemExit is not an Exception subclass, but a broader except clause added later would catch the exit and change the exit code.
