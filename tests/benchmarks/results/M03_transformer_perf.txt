M03 PERFORMANCE BOTTLENECKS: transformer.py (55 lines)

Method: static read of the source, plus a timing run on 100,000 records
(CSV-shaped dicts with 4 string fields, 3 default steps, best of 3, CPython).
Multipliers marked "measured" come from that run. The others are estimates.
N+1 patterns: none. I/O: none. The module is pure CPU and memory.

Baseline: apply(records, 3 steps) on 100k records = 0.131 s.

------------------------------------------------------------------
1. One full pass and one full copy of the data per step  [HIGH]
------------------------------------------------------------------
Location: apply(), lines 52-54.

    result = list(records)
    for step in steps:
        result = [_REGISTRY[step](r) for r in result]

Each step builds a new list of N records, and each step function builds a
new dict per record (dict(record) at lines 25 and 42, a dict comprehension
at line 36). With S steps the code allocates S*N dicts and S lists. All but
the final N dicts are garbage as soon as the next step finishes. Peak memory
holds two generations of the data at once (the list being read and the list
being built). The _REGISTRY[step] lookup also runs once per record instead
of once per step.

Fix: resolve the functions once, then run all of them over each record in a
single pass. Copy only once per record, at the start of the chain, and let
steps mutate that copy.

    fns = [_REGISTRY[s] for s in steps]
    out = []
    for r in records:
        for fn in fns:
            r = fn(r)
        out.append(r)
    return out

This keeps the "steps return a copy" contract but drops the intermediate
lists and the per-record registry lookup. Peak memory goes from about 2N
records to about N. A larger gain needs the in-place variant below.

Estimated improvement: 1.2x faster, about 1.5x less peak memory.

In-place variant (changes the public contract, so only with a yes): steps
take and mutate one private copy of each record. Then S*N dict copies become
N copies.

Measured: single-pass with all three steps fused into one dict build
0.083 s vs 0.131 s = 1.6x faster. Estimated for the in-place variant with the
registry lookup hoisted: 1.6x to 1.8x.

------------------------------------------------------------------
2. Redundant float() conversion in add_flag  [MEDIUM]
------------------------------------------------------------------
Location: add_flag(), line 43.

    out["flagged"] = float(out.get("value", 0)) > 100

When normalize_value ran earlier (the default order), "value" is already a
float. add_flag converts it again. When normalize_value did not run and
"value" is a non-numeric string, add_flag raises ValueError and aborts the
whole batch (a correctness risk, not just speed).

Fix: accept a float already in place and only convert when needed.

    v = out.get("value", 0)
    if not isinstance(v, float):
        v = float(v)
    out["flagged"] = v > 100

Estimated improvement: 1.1x on the add_flag step, under 1.05x on the whole
chain. Low value alone, but it costs nothing.

------------------------------------------------------------------
3. strip_whitespace rebuilds every field  [MEDIUM]
------------------------------------------------------------------
Location: strip_whitespace(), line 36.

The comprehension runs isinstance() and a method call on every field of
every record, and creates a new str even when the string has no whitespace
to strip (str.strip() returns the same object when nothing changes, so the
allocation is skipped, but the call overhead stays).

Fix: if the input is known to be clean (JSON input usually is), skip the
step. If the input is CSV with a known set of text columns, strip only those
columns (for example "name" and "timestamp"; "id" and "value" are consumed
by later steps anyway).

    out = dict(record)
    for k in _TEXT_COLUMNS:
        v = out.get(k)
        if isinstance(v, str):
            out[k] = v.strip()
    return out

Estimated improvement: 1.3x on this step for 4-column records, scaling with
column count. About 1.1x on the whole chain.

------------------------------------------------------------------
4. Redundant list(records) copy  [LOW]
------------------------------------------------------------------
Location: apply(), line 52.

The copy exists so that an empty steps list returns a new list instead of
the caller's. With one or more steps the first comprehension already makes a
new list, so the copy is wasted work.

Measured: 1.5 ms for 100k records, about 1% of total.

Fix: remove it, or fold it into the single-pass loop from item 1.

Estimated improvement: 1.01x.

------------------------------------------------------------------
5. Dict-per-record storage  [LOW, structural]
------------------------------------------------------------------
Each record is a dict with a hash table of its own. For large inputs a
tuple, a __slots__ class, or a dataclass(slots=True) uses roughly 2x to 3x
less memory per record. This changes the interface of every module in the
pipeline, so it is out of scope for a local fix.

Estimated improvement: about 2x memory, 1.2x speed. Not recommended for a
pipeline this small.
