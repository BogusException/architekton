(1) Name and line range
    main, cli.py lines 20-61 (called from the entry-point guard at lines 64-65).

(2) Time complexity
    O(B + s*n*m*L + n*k*L + O)
    With L bounded by a constant and B = O(n*m), this simplifies to
    O(n*m*(s + 1) + n*k + O), and since O <= n*(k + 1), to O(n*m*(s + 1) + n*k).
    For the defaults (s = 3, k = 3) this is O(n*m).

(3) Space complexity
    Auxiliary (excluding the report that is produced): O(n*m).
    Output (the ValidationReport and the rendered text): O(n + f) for the report object, and
    O(O) for the rendered string, which is O(n + f).
    Both are linear in the data; nothing grows faster than the input.

    Optional notes, not required by the flag rule. Both are constant-factor changes and do
    not change the Big-O class:

    a) apply() makes s separate passes and allocates s generations of n dicts. A single
       pass that composes the steps per record cuts allocations from s*n dicts to n dicts
       and lowers peak space. Time stays O(s*n*m*L). Sketch (a change to transformer.py,
       not to cli.py, and not applied here):

           def apply(records, steps):
               fns = [_REGISTRY[s] for s in steps]          # O(s), after the unknown check
               out = []
               for r in records:                            # n iterations
                   for fn in fns:                           # s calls, each O(m)
                       r = fn(r)
                   out.append(r)
               return out

    b) load_csv() and the pipeline hold the whole file in memory. If n becomes very large,
       a generator pipeline (load -> apply -> validate) would reduce auxiliary space from
       O(n*m) to O(m + k) plus the failure list. The report still needs O(n) result
       objects unless only failures are stored. This changes the public API of the four
       modules, so it is only worth doing if memory becomes a measured problem.
