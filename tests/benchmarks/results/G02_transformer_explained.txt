transformer.py cleans and enriches a list of records. A record is a plain dict, such as one row from a CSV or JSON file. The module keeps a registry of named transformation functions (the _REGISTRY dict at line 11). The register() decorator at line 14 adds a function to that registry under a name. Three transformations ship with the module: normalize_value (line 23) casts the "value" field to a float, strip_whitespace (line 34) trims every string field, and add_flag (line 40) adds a boolean "flagged" field that is True when the value is above 100. The one public entry point is apply() at line 47. It takes a list of records and a list of step names, and returns a new list with every step applied to every record.

The main caller is cli.py. It loads records with data_loader.load, calls apply() at line 55, and passes the result to validator.validate and then reporter.write. The default steps are listed in DEFAULT_STEPS at cli.py line 16, and users can override them with the steps option on the command line. A developer who adds a new cleanup rule to the pipeline would also use this module: write a function that takes a dict and returns a dict, then decorate it with @register("my_step"). A user of the command-line tool only picks step names and never touches the code.

Use this module when the steps must be chosen by name at run time, for example from command-line arguments or a config file. A list comprehension or map() is simpler when you have one fixed step that you know at write time. Pandas is a better choice for large tables, because it works on whole columns at once and this module calls a Python function for every record on every step. For the small files this pipeline handles, the registry adds a clear, testable list of allowed step names and a single place that rejects bad ones. If you only need one operation in one place, call the function directly and skip the registry.

Several details can surprise a new developer. First, the input is not changed. apply() copies the outer list at line 52, and each transformation builds a new dict (dict(record) at lines 25 and 42, a comprehension at line 36). The copy is shallow, though, so a nested list or dict inside a record is still shared with the original. Second, order matters. add_flag calls float() at line 43 with no try block, so a non-numeric or None value raises ValueError or TypeError if normalize_value has not run first. The default order in cli.py puts normalize_value before add_flag for this reason. Third, missing keys are handled differently in each function. normalize_value (line 27) treats a missing "value" as 0 and writes 0.0 into the record, which also adds the key. add_flag treats a missing "value" as 0 and sets "flagged" to False without adding "value". strip_whitespace ignores missing keys and non-string values, and it only touches top-level fields. Fourth, apply() checks every step name before it starts (lines 49 to 51) and raises one ValueError that lists all unknown names, which cli.py catches at line 59 and turns into exit code 2. A function that fails during a step is not caught, so one bad record stops the whole run and no partial result is returned. Finally, _REGISTRY is global state. Registering the same name twice (line 17) silently replaces the earlier function, and an empty steps list just returns a shallow copy of the input.
