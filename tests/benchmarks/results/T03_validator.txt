Purpose

validator.py checks a list of record dicts against named rules. A rule is a function that returns None when the record passes, or a string that describes the failure. validate() runs the chosen rules on every record and returns a ValidationReport with per-record results and an overall pass/fail. Three rules ship with the module: has_id, value_non_negative, name_not_empty.

Key functions

- rule(name) (lines 16-21): decorator factory that stores a function in the module-level _RULES dict (line 13) and returns it unchanged.
- has_id(record) (lines 25-28): fails when record.get("id") is falsy.
- value_non_negative(record) (lines 32-38): converts "value" with float() and fails when it is below 0. A TypeError or ValueError gives a "not numeric" message.
- name_not_empty(record) (lines 42-45): fails when str(record.get("name", "")).strip() is empty.
- RecordResult (lines 49-52): dataclass with record_id, passed, failures.
- ValidationReport (lines 56-64): dataclass with total, passed, failed, results and a computed property ok (failed == 0).
- validate(records, rules=None) (lines 67-93): picks the rules (all registered rules if none given), raises ValueError for unknown names, runs each rule on each record, prefixes every failure message with the rule name, and counts passes and fails.

Design choices

- Same registry-by-name pattern as transformer.py, so the CLI can pass strings.
- The "None means pass, string means failure" contract keeps rules simple and lets each rule give a specific message.
- All rule names are checked before any record is processed, so a typo fails at once.
- The validator does not stop at the first failure. It collects every failure for every record, which gives a complete report in one run.
- Failure messages carry the rule name ("has_id: missing or empty 'id'"), so the source of a failure is clear in the report.
- Results are dataclasses. The report has no I/O, so formatting stays in reporter.py.
- Python 3.10 or newer is required, because "str | None" is evaluated at import time on line 11.

Risks and missing error handling

1. Empty rules list means all rules (line 69). "rules or list(_RULES)" treats [] like None. A caller that passes an empty list on purpose, for example "--rules" with no names in cli.py, still gets every rule applied.
2. name_not_empty accepts None (line 43). str(None) is "None", which is not empty. A JSON record with "name": null passes the rule.
3. has_id rejects any falsy id, including the number 0 and False. An integer id of 0 is reported as missing.
4. value_non_negative lets NaN and inf pass. NaN < 0 is False. A missing "value" key counts as 0 and passes, so absent data is not reported.
5. No guard around rule calls (line 78). If a rule raises, or a record is not a dict (record.get fails with AttributeError), the whole run aborts with a traceback and no partial report. Custom rules have no isolation.
6. record_id is str(record.get("id", "(no id)")) (line 82). Records with a missing id show "(no id)". A record with id None shows "None" and one with an empty id shows an empty string. Duplicate ids are not detected, so report entries can be ambiguous.
7. total, passed and failed are stored fields as well as being derivable from results. A caller who builds a ValidationReport by hand can make them inconsistent.
8. A report with zero records is ok (failed == 0), so an empty input passes.
9. Registering a rule name that already exists silently replaces it, and _RULES is global state shared across tests.
10. Rules see the record after transformation. If normalize_value ran first, non-numeric values are already 0.0, and the "not numeric" branch in value_non_negative cannot trigger in the default pipeline.
