M03 PERFORMANCE BOTTLENECKS: data_loader.py (45 lines)

Method: static read of the source, plus a timing run on a 100,000-row,
4-column file in /tmp (best of 3, CPython, warm page cache). Multipliers
marked "measured" come from that run. The others are estimates.
N+1 patterns: none. Every function opens one file once.

Baseline: load_csv(100k rows) = 0.147 s. load_json(100k rows) = 0.081 s.

------------------------------------------------------------------
1. Whole file is materialized before the pipeline starts  [HIGH]
------------------------------------------------------------------
Location: load_csv() lines 17-26, load_json() lines 31-35.

Both loaders return a complete list[dict]. The pipeline then runs
transformer.apply (which makes more copies), validator.validate, and
reporter. Nothing downstream needs random access, but the file is read in
full, so peak memory is at least the size of the whole parsed dataset, and
the first output cannot appear until the last row is parsed.

This is also the main I/O blocking call. open() and the read happen on the
calling thread, and the rest of the pipeline waits for the entire file.

Fix for CSV: yield rows lazily.

    def iter_csv(path):
        with open(path, newline="") as fh:
            reader = csv.DictReader(fh)
            missing = REQUIRED_COLUMNS - set(reader.fieldnames or [])
            if missing:
                raise ValueError(...)
            yield from reader

transformer.apply and validator.validate would then take iterables. The
header check still runs before the first row is returned, as long as the
generator is primed once (call next() or wrap it) so errors still surface
before output starts.

Fix for JSON: json.load needs the whole document. For large files switch to
JSON Lines or an incremental parser (third-party ijson, which the project
rule "stdlib only in the hot path" rules out). With stdlib only, keep
json.load and accept the memory cost.

Estimated improvement (CSV): about 3x to 5x lower peak memory on large files
(only one row plus the final report lives at a time, but the report keeps
per-record results, so the full gain depends on item 1 in validator.py).
Wall time is unchanged to 1.1x faster. Estimate, not measured.

------------------------------------------------------------------
2. Redundant dict(row) copy per row  [MEDIUM]
------------------------------------------------------------------
Location: load_csv(), lines 24-25.

    for row in reader:
        rows.append(dict(row))

csv.DictReader already returns a fresh dict for every row (a plain dict
since Python 3.8; an OrderedDict in 3.6 and 3.7). The dict() call makes a
second copy of every row, and the explicit append loop is slower than
list().

Fix:

    rows = list(reader)

(After the header check. On Python 3.7 and older, dict() is needed to avoid
OrderedDict. The code already uses list[dict] and str | None syntax, so the
project requires 3.10 or later and this concern does not apply.)

Measured: 0.136 s vs 0.147 s = 1.08x faster, and one fewer dict allocated
per row (about 1.5x less peak memory during the load).

------------------------------------------------------------------
3. csv.DictReader per-row overhead  [MEDIUM]
------------------------------------------------------------------
Location: line 19.

DictReader builds a dict from the header for every row, and it checks for
blank rows in Python code. For a file with a known, fixed header,
csv.reader plus a tuple (or a namedtuple) skips that work. Using csv.reader
and zip(header, row) is not faster, so the real gain only comes if the rest
of the pipeline accepts tuples. Reading rows as tuples and delaying dict
creation until a record is validated is a design change.

Estimated improvement: 1.3x to 1.5x on load time, if downstream stages
accept sequences. Not recommended unless the loader is profiled as the top
cost on real data.

------------------------------------------------------------------
4. Text-mode read with default buffering  [LOW]
------------------------------------------------------------------
Location: lines 18 and 31.

open(path) decodes with the locale encoding and the default 8 KB buffer
(or the filesystem block size on newer Python). Two small things help on
large files:

  a) pass encoding="utf-8" explicitly. This avoids a locale lookup and
     removes a platform-dependent decode path (it also fixes a latent
     correctness issue on Windows).
  b) for json, open in binary mode and call json.load(fh). The stdlib
     json module decodes bytes itself and skips one decode layer.

Estimated improvement: 1.02x to 1.05x. Not measured.

------------------------------------------------------------------
5. Path(path) object and suffix check on every call  [NEGLIGIBLE]
------------------------------------------------------------------
Location: load(), lines 40-45.

One Path object per file load. Cost is microseconds against a file read.
Listed so nobody spends time on it.

------------------------------------------------------------------
I/O blocking summary
------------------------------------------------------------------
Single synchronous read per run. Threads or asyncio do not help (one file,
CPU-bound parsing, the GIL). For many input files, a
concurrent.futures.ProcessPoolExecutor over files gives close to linear
speedup per core. The CLI accepts one file today, so this does not apply.
